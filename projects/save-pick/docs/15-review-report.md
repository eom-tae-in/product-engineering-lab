## 2. 접점 정합성 검증 — X1~X8

`00-status.md`가 지목한 8개 접점을 각각 근거 문서·와이어프레임 원문과 대조했다.

### X1 · 화면 오류 상태 ↔ API 오류 코드 카탈로그 (11 §0.5)

지정된 4개 코드 기준으로 확인.

| 코드 | 06/와이어프레임 대응 화면 문구 | 판정 |
|---|---|---|
| `OUT_OF_STOCK` | SC-004 "방금 다른 고객이 먼저 담았어요" + 부족 목록, SC-005 시나리오 진입 전 차단 | 일치 |
| `CANCEL_NOT_ALLOWED` | SC-011 "이미 처리된 주문이에요" | 부분 일치 — 아래 X3 참조 |
| `ORDER_RESTRICTED` | SC-004/SC-005/SC-001 주문 제한 배너·시트 | 일치 |
| `INTERNAL_ERROR`(500, 재실행된 11번 문서 신규 추가분) | **없음** | **문제 있음** |

`INTERNAL_ERROR`는 `00-status.md` 중단·재개 이력에 기록된 대로 기술 트랙 재실행 중 §0.5에 새로 추가된 코드다(신규 1행). 디자인 트랙은 이 시점 이전에 이미 06을 완성했으므로 이 코드를 화면에 반영할 기회가 없었다 — 이번 재실행 재개 과정에서 발생한 전형적인 트랙 간 시차 결함이다. 13번 §3의 락 타임아웃(3초) 시나리오가 발생하면(주로 SC-004 "주문하기" 클릭 시점) 사용자에게 보일 화면이 정의돼 있지 않다. 부가로 두 가지를 추가 발견했다.

- `CART_ITEM_LIMIT_EXCEEDED`(장바구니 품목 10개 초과, BR-009)에 대응하는 화면 문구가 SC-003·SC-004 어디에도 없다.
- `SLOT_CLOSED`가 결제 시점(API-022 4단계, 13번 §4)에도 재검사되는데 SC-007의 오류 상태는 `SLOT_FULL`(정원 소진)만 정의하고 "결제 직전 예약 마감 경과"는 별도로 정의돼 있지 않다.

**판정: 문제 있음.** 소유: experience-designer(06 오류 상태 보강). 근거: 위 표, 09 §3.3.

### X2 · 선점 만료 중간 상태 ↔ 만료 시트 동작

13번 §2.2가 정의하는 "주문 PENDING·선점 EXPIRED 최대 30초 공존" 구간과 SC-005·006·007의 만료 시트를 대조했다.

- 09 §2.5·§3.3: 클라이언트는 `hold_expires_at`(=선점 만료 시각, 서버가 내려준 값) 기준 카운트다운이 0:00에 도달하는 즉시 만료 시트를 띄우고 모든 조작을 막는다.
- 13번 §2.2: 결제(API-022)·시간대 지정(API-021)은 `orders.hold_expires_at <= now()`를 결제·지정 이전에 검사해 `HOLD_EXPIRED`로 끝난다. 조회(API-018)도 `status: EXPIRED`를 즉시 반환한다.
- 두 값의 판정 기준(`hold_expires_at`)이 동일하고, 클라이언트가 0:00 이후 어떤 조작도 허용하지 않으므로 "선점은 이미 EXPIRED인데 화면은 아직 정상"으로 보이는 시나리오가 존재하지 않는다.

**판정: 문제 없음.** 두 트랙이 같은 기준 시각을 공유해 우연이 아니라 구조적으로 정합하다.

### X3 · 취소 재전송 ↔ 화면 정의

- 기술: 11번 API-025 오류표와 13번 §5(IC-A9)는 취소 재전송을 멱등 200이 아니라 `CANCEL_NOT_ALLOWED`(409)로 통일 처리한다고 명시한다.
- 디자인: SC-011은 "오류(상태 불일치)" 상태를 정의하지만 예시 문구가 `"이미 처리된 주문이에요. 현재 상태는 픽업 완료예요"` 하나뿐이다. `CANCEL_NOT_ALLOWED`는 COMPLETED·NO_SHOW·CANCELED 세 가지 상태 모두에서 발생하는데, 고객이 **자신이 방금 성공시킨 취소 요청을 재전송**(느린 응답으로 인한 재시도 등)하는 경우 실제 현재 상태는 CANCELED이지 COMPLETED가 아니다. 이 경우 화면이 하드코딩된 예시 문구("픽업 완료예요")를 그대로 노출하면 사실과 다른 안내가 된다.
- 완화 요인: 오류 시트에 `주문 상세로` 이동 버튼이 있어(SC-011 상태 표), 이동 후 SC-010에서는 실제 상태(취소됨)가 정확히 표시된다(SC-010 "취소 불가(CANCELED)" 상태 존재). 즉 최종적으로 사용자가 잘못된 정보만 보고 끝나지는 않는다.

**판정: 문제 있음(경미, 비차단).** SC-011의 "오류(상태 불일치)" 문구를 실제 상태(COMPLETED/NO_SHOW/CANCELED)에 따라 분기하도록 보완이 필요하다. 소유: experience-designer.

### X4 · 관리자 세션 수명 ↔ 매장 운영 시나리오

- 12번 §2.1은 관리자도 고객과 같은 액세스 30분/리프레시 30일(슬라이딩)을 쓴다고 명시했고, 스스로 AU-U1로 "매장 공용 단말이면 12시간이 적절"이라는 대안을 미확정으로 남겼다.
- 06/07의 관리자 화면·흐름(SC-101~113, FL-101~105)은 재발급이 12번 §2.3처럼 조용히(화면 전환 없이) 이뤄진다는 전제와 충돌하지 않는다 — 어떤 관리자 화면도 "30분마다 재로그인"을 요구하는 흐름을 그리지 않았고, 반대로 액세스 토큰 만료를 화면이 직접 처리해야 한다고 가정하지도 않았다.
- 즉 **기능적으로는** 화면과 세션 설계가 모순되지 않는다. 남은 것은 "매장 공용 단말이 로그아웃 없이 최대 30일간 유지되는 것이 보안·운영상 적절한가"라는 **정책 결정**이며, 이는 이미 기술 트랙 스스로 T2/AU-U1로 식별해 미확정 처리했다.

**판정: 문제 없음(기능적 모순 없음). 정책 결정 필요(T2/AU-U1, 기 식별).** 소유: 사용자/orchestrator(정책 확정) — 문서 결함 아님.

### X5 · 락 타임아웃 ↔ SC-004·005 오류 상태

- 13번 §3: `lock_timeout = 3s` 초과 시 `INTERNAL_ERROR`(500), 트랜잭션 전체 롤백.
- 06 SC-004 오류 상태 목록(재고 소진, 주문 제한, 진행 중 주문서 존재, 통신 오류)과 SC-005 오류 상태 목록(통신 오류) 어디에도 "일시적 시스템 오류로 주문서 생성 자체가 실패한 경우"에 대응하는 문구가 없다. SC-004의 "오류(통신)"는 장바구니 조회(GET) 실패 문구("장바구니를 불러오지 못했어요")로 한정돼 있어 주문서 생성(POST) 실패와는 다른 상황이다.

**판정: 문제 있음.** X1의 `INTERNAL_ERROR` 결함과 동일 근본 원인이다. 소유: experience-designer. 권고 문구 예: `"일시적인 오류로 주문서를 만들지 못했어요. 잠시 뒤 다시 시도해주세요"`.

### X6 · 픽업 정원 점유 시점 ↔ SC-006 "정원 마감" 표시 시점

- G1 확정값(00-status #9)·13번 §8·05 §8: 정원은 **결제 성공 시점**에만 점유되고 PENDING은 점유하지 않는다. `pickup_slots.reserved_count`는 결제 성공(+1)과 취소·노쇼(-1)에서만 변한다.
- 11번 API-020 응답 예시의 `reservedCount`는 CONFIRMED·READY·COMPLETED 합계이며 PENDING 선점 건수를 포함하지 않는다(BR-016과 일치).
- 06/09 SC-006의 "정원 마감(20/20)" 칩은 이 `reservedCount`를 그대로 노출하므로, 다른 고객의 미결제 PENDING이 남의 시간대를 "정원 마감"으로 잘못 보이게 만드는 일이 없다.

**판정: 문제 없음.** 표시 시점과 점유 시점이 같은 카운터(`reserved_count`)를 공유해 정합하다.

### X7 · 재고 변경 이력 화면(SC-106) ↔ `stock_ledgers.reason` 값 집합

가장 구체적인 결함이다. 세 가지 불일치를 발견했다.

| 구분 | 03(FR-047)·06(SC-106) 표시 사유 | 10·11·13(기술) 원장 `reason` 값 | 불일치 내용 |
|---|---|---|---|
| 1 | "선점 해제" 1개 | `HOLD_RELEASE`(결제 3회 실패/주문서 포기), `HOLD_EXPIRE`(TTL 만료) 2개 | 화면이 서로 다른 두 사유를 하나로 합쳐 표시한다. 기술 설계는 이 둘을 의도적으로 구분했다(13번 §4 표) |
| 2 | (표시 카테고리 없음) | `CANCEL_DISCARD`(마감 후 취소·폐기) | BR-019가 정의하는 "취소 시 재고 미복구·폐기" 결과에 대응하는 화면 사유 카테고리가 없다. "취소 복구"(`CANCEL_RESTORE`)만 있다 |
| 3 | "노쇼 미복구" | **없음** | BR-022·13번 §5는 "NO_SHOW 전환은 수량을 바꾸지 않으므로 `stock_ledgers` 행 자체를 만들지 않는다"고 명시한다. 즉 "노쇼 미복구"라는 원장 항목은 기술 설계상 **존재할 수 없다**. SC-106 와이어프레임은 이 항목의 예시 카드까지 만들어 넣었으나(실제 코드에서는 재현 불가능한 화면) |

세 번째가 가장 근본적이다. 근원은 `03-functional-requirements.md`의 FR-047 완료 조건이 "노쇼 미복구"를 재고 변경 **이력의 사유**로 요구한 데 있다. 그러나 노쇼는 정의상 수량이 변하지 않는 사건이므로(BR-022), "재고가 언제·왜 변했는지 추적한다"는 FR-047의 목적과 애초에 맞지 않는다. technical-architect는 이 모순을 BR-022 쪽(수량 불변 → 원장 미기록)으로 해소했지만, 그 결과 FR-047·06 쪽 요구사항이 충족 불가능한 상태로 남았다.

**판정: 문제 있음(3건, 그중 1건은 근본 모순).** 소유: product-planner(FR-047 완료 조건 재정의 — "노쇼 미복구"를 원장이 아니라 주문 상태 이력/노쇼 목록에서 확인하는 것으로 명확화 권고) 1차, 이어서 experience-designer(SC-106 필터 6종 → 기술 원장 값에 맞춰 재구성, "노쇼 미복구" 제거 또는 대체) 2차.

### X8 · 마감 자동 전환(BATCH-02) 이력 ↔ SC-106 표시

- 12번 §4.6: BATCH-02는 `product_change_logs.actor_id`가 NOT NULL이라 SYSTEM 주체로 기록할 수 없어 **아예 로그를 남기지 않는다**(AU-4, T7과 동일 사안).
- 그러나 SC-106은 `stock_ledgers`(재고 원장) 화면이지 `product_change_logs`(상품 정보 수정 이력) 화면이 아니다. `product_stocks`(재고 수량)는 상품이 CLOSED로 자동 전환될 때 전혀 변하지 않으므로, BATCH-02는 애초에 SC-106에 어떤 행도 만들지 않는다. 따라서 "SC-106에서 빈칸으로 보이는" 문제는 발생하지 않는다 — 애초에 그 화면에 나타날 이벤트가 아니다.
- 다만 06~09 어디에도 `product_change_logs`를 목록으로 보여주는 화면(가칭 "상품 수정 이력")이 없다(SC-104는 "마지막 수정 시각" 단일 값만 표시). 따라서 자동 마감 전환에 대한 감사 이력이 **어떤 화면에도 나타나지 않는 공백**이 존재하지만, 이는 "빈칸 노출"이 아니라 "표시할 화면 자체가 없음"이며, 애초에 API-107(상품 수정 이력 조회)에 대응하는 전용 화면이 06에 없다는 점(§1 표의 FR-041 매핑이 SC-104 하나뿐인 점)과 같은 근에서 나온 별개의 경미한 공백이다.

**판정: 문제 없음(SC-106 한정 — 빈칸 노출 없음). 별도의 경미한 공백 확인: `product_change_logs` 목록을 보여주는 전용 화면이 없어 자동 마감 전환의 감사 추적이 어디에도 노출되지 않는다(T7과 동일 근본 원인).** 소유: technical-architect(actor_id NULL 허용 여부 재검토) 또는 product-planner(자동 전환 이력이 실제로 필요한 요구사항인지 확인) — MVP 차단 사유는 아니다.

### 2. X1 · X3 · X5 · X7 · D3 · D4 재판정

#### X1 (화면 오류 ↔ API 오류 코드 카탈로그) — **해소**

`CART_ITEM_LIMIT_EXCEEDED`(11번 §0.5 · 69행), `INTERNAL_ERROR`(11번 §0.5 · 94행), `SLOT_CLOSED`(11번 §0.5 · 815행 및 API-022 오류표)를 06 원문과 백틱 코드명까지 문자 그대로 대조한 결과 세 코드 모두 정확히 일치하는 이름으로 06에 반영됐다. `SLOT_FULL`(정원 소진, 기존에 이미 정의됨)과 `SLOT_CLOSED`(예약 마감, 이번에 추가됨)가 SC-007에서 서로 다른 문구·다른 대안 경로(둘 다 "다른 시간대 고르기"로 SC-006 유도하되 사유 문구는 구분)로 분리 정의돼 혼동 여지가 없다.

#### X3 (취소 재전송 ↔ 화면 정의) — **문서 수준 해소, 와이어프레임 수준 경미한 잔여**

06 SC-011의 "오류(상태 불일치)" 문구가 실제 현재 상태(COMPLETED/CANCELED/NO_SHOW) 3분기 표로 재정의돼, 재전송 시나리오(취소 성공 직후 재요청)에서도 CANCELED 분기가 적용되어 "이미 취소된 주문이에요"를 정확히 보여준다. **06 문서 자체는 해소.**

다만 `wireframes/sc-011-order-cancel.html`을 열어 실제 인터랙티브 목업을 확인한 결과, "오류(상태 불일치)" 토글은 여전히 1개(`conflict`)뿐이고 하드코딩된 문구도 `이미 처리된 주문이에요 / 현재 상태는 픽업 완료예요`(COMPLETED 사례) 하나만 남아 있다. CANCELED·NO_SHOW 분기는 06 문서에는 있으나 이 와이어프레임 파일에서 클릭으로 확인할 수 없다. 이는 1차 검토가 D5(SC-111 대표 7개 시간대만 렌더)에 적용한 "설계 문서 vs 예시 프로토타입 축약" 판단 기준과 동일한 성격의 경미한 잔여이며, 06 명세 자체는 완전하므로 게이팅 사유로 보지 않는다. experience-designer에게 후속 참고로 기록만 한다.

#### X5 (락 타임아웃 ↔ SC-004·005 오류 상태) — **해소**

SC-004·SC-005·SC-007 세 화면 모두에 `INTERNAL_ERROR`(500) 대응 문구가 추가됐고, 문구 아래 "재고 행 락 대기가 3초를 넘는 등 시스템 오류이며 트랜잭션 전체가 롤백돼 재고·주문 상태는 바뀌지 않는다(13번 §3)"로 근거 조항까지 정확히 인용했다. 신설된 가정 A13("`INTERNAL_ERROR` 발생 시 결제 재시도 횟수·재고·주문 상태를 모두 그대로 둔다")도 13번 §3·§4의 "트랜잭션 전체 롤백"·"`payment_attempts` 행 자체가 생기지 않는다" 서술과 정합한다.

#### X7 (재고 변경 이력 사유 ↔ `stock_ledgers.reason`) — **3건 모두 해소, 3문서 1:1 일치 확인**

세 문서(03·06·13)와 와이어프레임(sc-106)을 라벨 단위로 대조한 결과는 다음과 같다.

| 원장 `reason`(13번) | 03 FR-047 완료 조건 | 06 SC-106 필터·대응표 | wireframes/sc-106 필터·카드 |
|---|---|---|---|
| `ADMIN_ADJUST` | 관리자 조정 | 관리자 조정 | 관리자 조정 |
| `HOLD` | 선점 | 선점 | 선점 |
| `HOLD_RELEASE` | 선점 해제 | 선점 해제 | 선점 해제 |
| `HOLD_EXPIRE` | 선점 만료 | 선점 만료 | 선점 만료 |
| `CONFIRM` | 확정 차감 | 확정 차감 | 확정 차감 |
| `CANCEL_RESTORE` | 취소 복구 | 취소 복구 | 취소 복구 |
| `CANCEL_DISCARD` | 취소 폐기 | 취소 폐기 | 취소 폐기 |

4개 문서(03·06·13·wireframe) 모두 정확히 7개, 라벨 표기까지 글자 단위로 일치한다. 세부적으로:

1. "선점 해제" 1개로 뭉뚱그려졌던 문제 — `HOLD_RELEASE`(선점 해제)와 `HOLD_EXPIRE`(선점 만료)가 03·06 모두에서 별도 항목으로 분리됨. **해소.**
2. `CANCEL_DISCARD`에 대응하는 화면 카테고리 부재 — "취소 폐기" 항목이 03·06에 신설됨. **해소.**
3. "노쇼 미복구"(존재할 수 없는 원장 항목) — 03에서 완전히 삭제되고 대체 안내로 교체됨, 06도 "노쇼 관련 사유 항목을 두지 않는다"고 명시적으로 배제함. **해소(근본 모순 제거).**

#### D3 (상품 카드 높이 128px vs 실제 ~170px) — **해소**

09 §2.4·A4가 "약 170px"로 갱신되고 근거로 실제 와이어프레임 파일명까지 명시했다. 수치 명세와 구현이 이제 같은 값을 가리킨다.

#### D4 (SC-112 카운트다운 배지 ↔ 08 §2.3 원칙) — **해소 (문언상 충돌 없음으로 재확인)**

08 §2.3 원칙은 "상품 목록·상세에 초 단위 카운트다운을 두지 않는다"이다. 06 SC-112는 (a) 상품 목록·상세가 아닌 관리자 노쇼 화면이고, (b) 초 단위가 아닌 분 단위 표시이며, (c) 매초 갱신이 아니라 "목록을 다시 불러올 때 다시 계산"하는 정적 값이라고 06 자체가 명시한다. 08 문서는 수정되지 않았고 수정할 필요도 없다 — 06이 08의 제한 범위(상품 목록·상세, 초 단위) 밖에서 별도 규칙을 신설한 것이므로 텍스트 수준에서 저촉되지 않는다.

### 6. G4(발행) 최종 판정

**G4 진행 가능.**
