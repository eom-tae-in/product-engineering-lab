## 1. 인증 방식

### 1.1 자격 증명

| 항목 | 값 | 근거 |
|---|---|---|
| 로그인 식별자 | 이메일 (소문자 정규화 후 비교) | 03 A1, 10번 `members.email` UNIQUE |
| 비밀번호 최소 길이 | 8자 | 03 A2, FR-001 |
| 해시 알고리즘 | bcrypt, cost 12 | 10번 `members.password_hash`. 단방향, 솔트 내장 |
| 평문 저장·로그 출력 | 금지 | 요청 본문 로깅에서 `password` 필드를 마스킹한다 |

이메일과 비밀번호 중 무엇이 틀렸는지 구분해 알리지 않는다. 두 경우 모두 `INVALID_CREDENTIALS`(401)이며 응답 본문과 응답 시간이 같아야 한다. 미가입 이메일이어도 해시 비교를 수행하는 더미 경로를 태워 응답 시간 차이로 가입 여부가 드러나지 않게 한다 (FR-002, BR-002).

### 1.2 로그인 시도 차단

- 판정 근거는 `login_attempts` 테이블이다 (10번 §2.3).
- 조건: **같은 이메일**에 대해 마지막 성공 이후 연속 실패가 5건 이상이고, 5번째 실패 시각 + 10분이 아직 지나지 않았으면 차단한다 (03 A3, FR-002).
- 응답: `LOGIN_BLOCKED`(429), `details.retryAfterAt`에 차단 해제 시각을 담는다.
- 차단 중에는 비밀번호가 맞아도 로그인시키지 않고, `login_attempts`에 시도 행을 추가하지 않는다. 추가하면 차단이 무한 연장된다.
- 잠금 대상은 계정(이메일)이지 IP가 아니다. `client_ip`는 기록만 하고 판정에 쓰지 않는다. 단일 매장 규모에서 IP 기준 차단은 같은 건물·회사에서 접속하는 정상 고객을 함께 막는다.

### 1.3 토큰 구조

| 토큰 | 형식 | 전달 방식 | 서버 상태 |
|---|---|---|---|
| 액세스 토큰 | JWT (HS256 서명) | `Authorization: Bearer <token>` 헤더 | 없음 (자체 검증) |
| 리프레시 토큰 | 불투명 난수 32바이트 (Base64URL) | `HttpOnly` 쿠키 | 있음 (`auth_sessions` 1행) |

액세스 토큰 클레임

| 클레임 | 값 | 용도 |
|---|---|---|
| `sub` | `members.id` | 주체 식별 |
| `role` | `CUSTOMER` / `ADMIN` | 인가 판정 (BR-002) |
| `sid` | `auth_sessions.id` (UUID) | 세션 폐기 추적, 감사 로그 |
| `iat`, `exp` | 발급·만료 시각 (epoch) | 만료 판정 |
| `typ` | `access` | 리프레시 토큰을 액세스 토큰으로 쓰는 혼동 차단 |

- 리프레시 토큰은 JWT로 만들지 않는다. 서버가 즉시 폐기할 수 있어야 하므로 의미 없는 난수여야 한다.
- 리프레시 토큰 원문은 저장하지 않는다. SHA-256 해시를 `auth_sessions.refresh_token_hash`(UNIQUE)에 넣는다 (10번 §2.2). DB가 유출돼도 토큰을 복원할 수 없다.
- 액세스 토큰에 이름·이메일·전화번호를 넣지 않는다. 토큰이 개인정보 저장소가 되면 회원 정보 수정(FR-003) 시 토큰이 낡는다.

### 1.4 리프레시 쿠키 속성

| 속성 | 값 | 이유 |
|---|---|---|
| 이름 | `sp_refresh` | 고객·관리자 공용. `POST /api/auth/logout`(API-004)을 두 주체가 함께 쓰기 때문이다 |
| `HttpOnly` | true | 스크립트가 토큰을 읽지 못하게 한다 (11번 A-A10) |
| `Secure` | true | HTTPS 전송만 허용 |
| `SameSite` | `Lax` | 재발급·로그아웃은 자사 출처에서만 호출된다. 크로스 사이트 POST를 차단해 CSRF 표면을 줄인다 |
| `Path` | `/api` | 상품 조회 같은 요청에도 쿠키가 붙지만, 경로를 `/api/auth`로 좁히면 관리자 경로에서 로그아웃이 불가능해진다 |
| `Max-Age` | 30일 (2,592,000초) | 세션 수명과 일치시킨다 |

## 2. 토큰 수명과 갱신

### 2.1 수명 확정값

| 항목 | 값 | 근거 |
|---|---|---|
| 액세스 토큰 수명 | **30분** | 11번 API-001·API-002 응답 예시(`serverTime` +30분)와 일치 |
| 리프레시 세션 수명 | **마지막 활동 후 30일** (슬라이딩) | FR-002 완료 조건, 03 A4, 10번 `auth_sessions.expires_at = last_used_at + 30일` |
| 시계 오차 허용치 | 30초 | 서버 간 시각 편차 흡수. 클라이언트 시각은 신뢰하지 않는다 (BR-028) |
| 만료 세션 물리 삭제 | `expires_at < now() - 7일` | BATCH-06, 10번 §8 |

액세스 토큰을 30분으로 잡은 이유

- 선점 유효 시간이 10분이다 (BR-007). 주문서 생성 → 시간대 선택 → 결제 3회 시도까지의 최장 흐름이 토큰 하나 안에서 끝나야 흐름 도중 401이 나지 않는다.
- 30분이면 로그아웃 후 토큰이 살아 있는 최대 구간도 30분으로 제한된다 (§2.4).
- 관리자도 같은 30분을 쓴다. 매장 공용 단말을 고려하면 더 짧은 값이 낫지만 G1 확정 범위 밖이므로 §가정에 제안으로만 남긴다.

### 2.2 재발급 (API-003 `POST /api/auth/token/refresh`)

처리 순서 (하나의 트랜잭션)

1. `sp_refresh` 쿠키를 읽는다. 없으면 `UNAUTHENTICATED`(401).
2. 쿠키 값을 SHA-256 해시해 `auth_sessions`를 `refresh_token_hash`로 조회하고 그 행을 `FOR UPDATE`로 잠근다. 없으면 401.
3. `revoked_at IS NOT NULL`이면 401. `expires_at <= now()`이면 401.
4. 새 리프레시 토큰을 생성해 같은 행의 `refresh_token_hash`를 교체하고, `last_used_at = now()`, `expires_at = now() + 30일`로 갱신한다 (**회전**).
5. 새 액세스 토큰(30분)을 발급하고 새 리프레시 쿠키를 `Set-Cookie`로 내려준다.

응답은 11번 API-003 그대로 `{ accessToken, accessTokenExpiresAt }`이며 리프레시 토큰은 본문에 넣지 않는다.

**왜 회전(rotation)인가**
쿠키가 한 번 유출되면 회전 없이는 30일간 계속 쓸 수 있다. 회전하면 탈취자와 정상 사용자 중 한쪽만 계속 성공하고, 다른 쪽이 401을 받아 재로그인하게 되어 피해 구간이 짧아진다.

**포기한 대안**
- 회전 없이 만료까지 같은 리프레시 토큰 사용: 구현은 단순하지만 유출 시 30일 노출. 기각.
- 재사용 탐지(옛 토큰이 다시 오면 해당 회원의 전 세션 폐기): `auth_sessions`에 이전 해시 컬럼이 필요해 10번 스키마를 바꿔야 한다. 첫 버전 범위 밖으로 두고 §미확정 AU-2에 남긴다.

**회전의 부작용과 처리**
탭을 여러 개 열어 두면 두 요청이 같은 쿠키로 동시에 재발급을 시도해 한쪽이 401을 받을 수 있다. 클라이언트는 재발급 요청을 **직렬화**하고(진행 중인 재발급이 있으면 그 결과를 공유), 재발급 401을 받으면 재시도하지 않고 로그인 상태를 종료한다. 서버는 3단계의 행 락으로 두 요청이 동시에 성공하는 경우를 막는다.

### 2.3 액세스 토큰 만료 시 클라이언트 동작

```
요청 → 401 UNAUTHENTICATED
  → POST /api/auth/token/refresh 1회 시도
      → 200: 새 액세스 토큰으로 원 요청 1회 재시도
      → 401: 인증 상태 종료. 원 요청을 재시도하지 않는다
```

- 재발급 재시도는 최대 1회다. 무한 루프를 만들지 않는다.
- 결제 요청(API-022)의 재시도는 예외다. `Idempotency-Key`가 같으면 앞선 시도 결과를 반환하므로 시도 횟수가 소모되지 않는다 (11번 API-022, BR-012). 토큰 만료로 인한 재시도가 결제 3회 한도를 깎지 않게 하는 장치다.

### 2.4 로그아웃 (API-004 `POST /api/auth/logout`)

1. 액세스 토큰의 `sid` 또는 쿠키 해시로 `auth_sessions` 행을 찾는다.
2. `revoked_at = now()`로 갱신한다. 이미 채워져 있으면 덮어쓰지 않는다.
3. `sp_refresh` 쿠키를 `Max-Age=0`으로 만료시킨다.
4. 204를 반환한다.

**폐기 범위**: 해당 세션 1건만 폐기한다. 다른 기기의 세션은 유지한다. 전 세션 폐기는 비밀번호 변경 기능이 생길 때 필요하며 첫 버전에는 그 기능이 없다.

**액세스 토큰의 잔존 구간**: 액세스 토큰은 서버 상태가 없으므로 로그아웃 후에도 최대 30분간 유효하다. 이 구간을 감수하는 이유는, 없애려면 매 요청마다 세션 조회나 폐기 목록 조회가 필요해 모든 API에 DB 왕복이 1회씩 늘기 때문이다. 대신 아래로 위험을 낮춘다.

- 30분 안에 끝나지 않는 위험 동작은 없다. 주문 확정·취소는 모두 소유권 검사(§3.3)를 다시 통과해야 한다.
- 재고·주문 상태를 바꾸는 모든 요청은 `orders.member_id`와 토큰 `sub`를 대조한다. 토큰만으로는 타인 주문에 접근할 수 없다.
- 관리자 계정 탈취가 의심되면 운영자가 `auth_sessions`의 해당 회원 행을 모두 `revoked_at` 처리하고 비밀번호를 재설정한다(운영 절차, API 없음).

**포기한 대안**: 액세스 토큰 폐기 목록(블랙리스트)을 캐시에 유지하는 방식. 모든 요청에 캐시 조회가 붙고, 캐시가 죽으면 인증 전체가 흔들린다. 30분 수명으로 위험을 시간으로 제한하는 편이 단순하다.

### 2.5 관리자 로그인 (API-101 `POST /api/admin/auth/login`)

- 경로만 다르고 토큰 구조·수명은 고객과 같다.
- `members.role = 'CUSTOMER'`이면 인증이 성공해도 `FORBIDDEN`(403)을 반환하고 토큰을 발급하지 않는다. 회원 정보를 응답에 담지 않는다 (FR-004).
- 반대로 `members.role = 'ADMIN'` 계정이 고객 로그인(API-002)을 호출하면 `FORBIDDEN`(403)이다. 관리자 흐름과 고객 흐름을 경로에서 분리하기 위함이다 (02 U4, 11번 §0.1).
- 로그인 차단(5회 10분)은 두 경로가 `login_attempts`를 공유한다. 경로를 바꿔가며 시도해도 차단을 우회할 수 없다.

## 3. 인가 판정

### 3.1 판정 순서

```
1. 경로가 /api/admin/* 인가?            → 예: role = ADMIN 이 아니면 403 FORBIDDEN
2. 엔드포인트가 인증을 요구하는가?        → 예: 유효한 액세스 토큰이 없으면 401 UNAUTHENTICATED
3. 엔드포인트가 고객 전용인가?           → 예: role = ADMIN 이면 403 FORBIDDEN
4. 리소스 소유자인가? (주문·장바구니·회원) → 아니면 404 NOT_FOUND
5. 업무 규칙 통과 여부 (주문 제한·상태·재고) → 각 API의 409 / 403 오류 코드
```

1~3단계는 공통 필터에서, 4단계는 각 서비스의 조회 조건에서, 5단계는 도메인 서비스에서 판정한다. 4단계를 컨트롤러에 흩어 두지 않는다.

### 3.2 401 / 403 / 404 구분 기준

| 상황 | 코드 | HTTP | 근거 |
|---|---|---|---|
| `Authorization` 헤더 없음 | `UNAUTHENTICATED` | 401 | 누구인지 모른다 |
| 액세스 토큰 서명 불일치·형식 오류 | `UNAUTHENTICATED` | 401 | 위조 토큰 |
| 액세스 토큰 `exp` 경과 | `UNAUTHENTICATED` | 401 | 클라이언트가 재발급을 시도해야 한다 |
| 리프레시 세션 폐기·만료 | `UNAUTHENTICATED` | 401 | 재로그인 필요 |
| 고객 토큰으로 `/api/admin/*` 접근 | `FORBIDDEN` | 403 | 누구인지는 알지만 권한이 없다 (BR-002, FR-004) |
| 관리자 토큰으로 고객 주문 API 접근 | `FORBIDDEN` | 403 | 11번 §0.1 |
| 관리자 로그인 경로에 고객 계정 | `FORBIDDEN` | 403 | FR-004 |
| 타인의 주문 조회·취소·결제 | `NOT_FOUND` | 404 | 존재 여부를 노출하지 않는다 (11번 API-018·024·025) |
| 노쇼 누적 주문 제한 계정의 주문서 생성 | `ORDER_RESTRICTED` | 403 | BR-023. 인증은 유효하고 특정 행위만 금지 |

403 응답에는 어떤 리소스 데이터도 담지 않는다. `code`, `message`, `serverTime`만 반환한다 (BR-002 "어떤 데이터도 반환하지 않는다").

### 3.3 소유권 판정 대상

| 리소스 | 판정 방법 | 실패 응답 |
|---|---|---|
| 주문 (`orders`) | `orders.member_id = 토큰 sub` | 404 `NOT_FOUND` |
| 회원 정보 (`members`) | 경로에 회원 ID를 두지 않고 `/api/me`로만 접근 | — (구조로 차단) |
| 장바구니 (`carts`) | 로그인 시 `carts.member_id = sub`, 비로그인 시 `carts.guest_token = X-Guest-Token` | 404 `NOT_FOUND` |
| 장바구니 품목 (`cart_items`) | `cart_items.cart_id`가 위에서 확정한 장바구니와 같은지 | 404 `NOT_FOUND` |

회원 정보를 `/api/members/{id}`가 아니라 `/api/me`로 둔 이유는, 경로에 남의 ID를 넣을 수 있는 구조 자체를 만들지 않기 위함이다.

### 3.4 게스트 토큰 (`X-Guest-Token`)

- 비로그인 장바구니 식별자이며 **인증 수단이 아니다**. 이 헤더만으로는 어떤 주문·회원 기능도 사용할 수 없다.
- 서버가 발급한다. 장바구니 담기(API-013) 요청에 헤더가 없으면 서버가 UUID를 생성해 응답에 담고, 클라이언트가 이후 요청에 붙인다.
- 신뢰 경계: 토큰 소지자를 장바구니 소유자로 본다. 장바구니에는 개인정보가 없고 재고에도 영향을 주지 않으므로(BR-010) 이 정도 보증으로 충분하다.
- 로그인·가입 시 `guestToken`을 본문으로 함께 보내면 회원 장바구니로 병합하고 게스트 장바구니를 삭제한다 (API-001, API-002, 10번 §5.1).
- 게스트 장바구니는 7일 미사용 시 삭제한다 (BATCH-06).

## 5. 보안 처리 규칙

| # | 항목 | 처리 |
|---|---|---|
| P1 | 전송 구간 | 전 구간 HTTPS. HTTP 요청은 308로 리다이렉트하고 쿠키를 내려주지 않는다 |
| P2 | CSRF | 상태 변경 API는 `Authorization` 헤더의 액세스 토큰으로 인가한다. 쿠키만으로 인가되는 API는 재발급·로그아웃뿐이며 `SameSite=Lax`로 막는다 |
| P3 | CORS | 허용 출처를 화이트리스트로 고정하고 `Allow-Credentials: true`를 함께 쓴다. 와일드카드 출처를 쓰지 않는다 |
| P4 | 응답 로깅 | `password`, `accessToken`, `Set-Cookie`, `refreshToken`은 로그에서 마스킹한다 |
| P5 | 오류 메시지 | 스택 트레이스·SQL·내부 식별자를 응답에 담지 않는다. `code`와 사람이 읽는 `message`만 반환한다 |
| P6 | 열거 공격 | 회원가입의 `EMAIL_DUPLICATED`는 가입 여부를 노출하지만, 이 응답이 없으면 가입 자체가 불가능하다. 로그인·비밀번호 경로에서는 노출하지 않는다 |
| P7 | 관리자 계정 생성 | API로 만들지 않는다. 운영자가 DB 마이그레이션·운영 스크립트로 `role = 'ADMIN'`을 부여한다 (03 A11, FR-004 예외) |
| P8 | 토큰 서명 키 | 환경 변수로 주입하고 저장소에 커밋하지 않는다. 키 교체 시 기존 액세스 토큰은 즉시 무효가 되고 클라이언트는 재발급 경로로 복구한다 |

## 6. 인증 관련 상태와 데이터 흐름

```
[가입/로그인]
  members 조회 → login_attempts 기록 → auth_sessions INSERT
  → 액세스 토큰(30분) + sp_refresh 쿠키(30일)

[일반 요청]
  액세스 토큰 검증(서명·exp·typ) → sub, role 확보 → 경로·역할 검사 → 소유권 검사 → 업무 규칙

[재발급]
  쿠키 해시 → auth_sessions FOR UPDATE → 유효성 검사
  → refresh_token_hash 교체 + last_used_at/expires_at 갱신 → 새 액세스 토큰

[로그아웃]
  auth_sessions.revoked_at = now() → 쿠키 만료

[정리]
  BATCH-06: expires_at < now() - 7일 세션 삭제, 90일 지난 login_attempts 삭제
```

`auth_sessions`는 액세스 토큰 검증 경로에서 조회하지 않는다. 재발급·로그아웃에서만 읽는다. 일반 요청에 DB 왕복을 추가하지 않기 위한 선택이며, 그 대가가 §2.4의 잔존 구간이다.

| # | 가정한 내용 | 근거 | 틀릴 경우 영향 |
