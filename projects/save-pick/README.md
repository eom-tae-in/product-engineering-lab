# Save Pick

마감이 임박한 신선식품을 할인가로 판매하고, 고객이 원하는 시간에 매장에서 직접 픽업하도록 연결하는 온라인 주문·픽업 서비스입니다.

첫 버전(MVP)은 단일 매장, 매장 픽업 전용 수령, 성공·실패만 판정하는 가상 결제를 전제로 합니다.

## 해결하려는 사용자 문제

| 문제 | 현재 상황 | Save Pick의 해결 |
|---|---|---|
| 매장의 마감 폐기 손실 | 마감 시각까지 팔리지 않은 신선식품은 전량 폐기된다 | 남은 시간에 따라 자동으로 할인해 판매 기회를 늘린다 |
| 할인 정보의 비대칭 | 고객은 매장에 직접 가야 마감 할인 여부를 안다 | 온라인에서 현재 할인가와 잔여 수량을 확인한다 |
| 헛걸음 | 매장 도착 시 이미 품절인 경우가 있다 | 주문 시 재고를 확정해 수령을 보장한다 |
| 픽업 시각 혼잡 | 마감 직전 고객이 몰려 응대가 어렵다 | 픽업 시간대를 나눠 예약받아 분산한다 |

## 서비스 목표

- 폐기 직전 재고를 매출로 전환하고, 마감 할인 대상 상품의 소진율을 높인다.
- 재고 임시 선점으로 "주문했는데 매장에 없는" 상황을 없앤다.
- 픽업 시간대 분산으로 마감 직전 응대 혼잡을 줄인다.

서비스 공개 후 8주를 기준으로 마감 소진율(60% 이상), 픽업 완료율(90% 이상), 노쇼율(5% 이하) 등의 지표로 성과를 측정할 계획입니다. (`docs/01-service-plan.md` §6)

## 주요 사용자

| 구분 | 정의 | 핵심 동기 |
|---|---|---|
| 고객 | 매장을 직접 방문할 수 있는 인근 생활권 소비자 | 신선식품을 정가보다 싸게 사는 것 |
| 관리자 | 매장 운영자 또는 매장 직원 | 폐기 손실을 줄이고 픽업 응대 부담을 예측 가능하게 만드는 것 |

## 핵심 기능 (MVP)

| 영역 | 내용 |
|---|---|
| 계정 | 회원가입, 로그인/로그아웃, 회원 정보 조회·수정 |
| 상품 | 목록, 검색, 정렬·필터, 상세, 마감 할인가·잔여 수량 표시 |
| 구매 | 장바구니, 주문서 생성과 재고 임시 선점(10분), 픽업 날짜·시간대 선택 |
| 결제 | 가상 결제(성공·실패 판정), 실패 시 재시도(최대 3회) |
| 사후 관리 | 주문 내역·상세 조회, 고객 취소, 노쇼 자동 판정과 제재 |
| 운영(관리자) | 상품·재고·주문·픽업 시간대 관리 |

**MVP에서 제외**: 실제 결제 연동, 실시간 배송·라이더 배정, 지도·위치 추적, AI 추천, 다중 매장 재고 연동. (`docs/01-service-plan.md` §5.2)

## 사용자 이용 흐름

```
상품 목록/검색 → 상품 상세(할인가·잔여 수량 확인) → 장바구니
   → 주문서 생성(재고 임시 선점, 10분) → 픽업 날짜·시간대 선택
   → 가상 결제(성공/실패, 실패 시 최대 3회 재시도) → 픽업 번호 발급
   → 매장 픽업 완료 (또는 픽업 시작 1시간 전까지 고객 취소)
```

## 관리자 기능

- 상품 등록·수정, 판매 상태 전환 (재고 미등록 상품은 판매 중으로 전환 불가)
- 재고 조정 (이미 선점·확정된 수량 미만으로는 축소 불가)
- 픽업 번호 기반 주문 조회, 준비 완료·픽업 완료 처리
- 사유를 남기는 관리자 취소
- 영업시간·픽업 정원·시간대 차단 설정

## 주요 설계 및 기술적 고민

- **재고 정합성 이중 방어선**: 애플리케이션 로직(비관적 락 `SELECT ... FOR UPDATE`) 이전에 DB `CHECK` 제약(`total - held - confirmed >= 0`)으로 초과 판매를 물리적으로 차단합니다. (`docs/10-erd.md`, `docs/13-inventory-concurrency.md`)
- **재고 임시 선점과 만료**: 주문서 생성 시 10분간 재고를 선점하고, 결제 미완료 시 자동 만료·복구합니다. 만료 배치와 결제 확정이 동시에 진행되는 경쟁 상황은 조건부 UPDATE로 한쪽만 성공하도록 설계했습니다.
- **멱등성**: 재고 변동 원장(`stock_ledgers`)에 `(order_id, product_id, reason)` 유니크 제약을 걸어, 같은 종결 처리(확정·해제·복구)가 중복 실행되지 않도록 물리적으로 막습니다.
- **도메인 우선 계층 구조**: 폴더를 `controller/service` 같은 기술 계층이 아니라 `account/store/product/stock/cart/pickup/order` 같은 도메인으로 먼저 나누고, 그 안에서 `api/application/domain/infrastructure` 4계층을 반복합니다. 업무 규칙 하나를 고치기 위해 여러 최상위 폴더를 오가지 않도록 하기 위함입니다.
- **시각의 단일 출처**: 모든 시각 판정은 `ServerClock`(주입 가능한 `Clock`)을 거치며, 선점 만료·취소 마감처럼 단일 트랜잭션 안에서 비교하는 판정은 DB의 `now()`를 기준으로 합니다.

## 실행 방법

### 백엔드

```bash
cd backend
docker compose up -d                          # 로컬 PostgreSQL 15 기동
SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun  # Flyway 마이그레이션 + 데모 데이터 자동 생성
curl http://localhost:8080/actuator/health
```

`application.yml`의 JWT 시크릿은 로컬 개발용 기본값을 갖고 있고 그 값이 저장소에 공개돼 있다. 그대로 운영에 뜨면 누구나 액세스 토큰을 위조할 수 있어, `dev`·`test`가 아닌 프로파일에서 기본값이면 `JwtSecretGuard`가 **기동을 거부**한다. 로컬에서 프로파일 없이 띄우려면 `JWT_SECRET`을 직접 주면 된다.

```bash
JWT_SECRET=$(openssl rand -base64 48) ./gradlew bootRun   # 프로파일 없이 띄울 때
```

`dev` 프로파일로 띄우면 `DevDataSeeder`가 최초 1회 데모 데이터를 넣는다. 12번(§5 P7)이 관리자 가입 API를 두지 않기로 해서, 로컬에서는 이 시드가 관리자 계정을 만드는 경로다(운영은 아래 「첫 관리자 계정 만들기」 참고).

| 계정 | 이메일 | 비밀번호 |
|---|---|---|
| 관리자 | `admin@savepick.kr` | `adminpass1` |
| 고객 | `customer@savepick.kr` | `savepick123` |

상품 5개(마감까지 남은 시간이 달라 할인 구간 0·30·50·70%가 모두 보인다)와 재고도 함께 들어간다. 픽업 시간대는 기동 시 BATCH-05가 D+0·D+1에 자동 생성한다. 프로파일 없이 띄우면 시드가 돌지 않는다.

### 첫 관리자 계정 만들기 (운영)

`dev` 시드는 운영에서 돌지 않으므로, 운영 환경에는 관리자 계정을 만드는 별도 경로가 필요하다. 12번(§5 P7)이 "운영자가 마이그레이션·운영 스크립트로 부여한다"고 정한 그 스크립트가 `AdminBootstrapRunner`다. 환경변수 넷을 주고 **한 번만** 띄우면 된다.

```bash
ADMIN_BOOTSTRAP_EMAIL=admin@example.com \
ADMIN_BOOTSTRAP_PASSWORD='<8자 이상>' \
ADMIN_BOOTSTRAP_NAME='매장 관리자' \
ADMIN_BOOTSTRAP_PHONE=01012345678 \
JWT_SECRET=... ./gradlew bootRun
```

- 넷 다 비어 있으면(기본) 아무 일도 하지 않는다.
- 일부만 채우거나 형식이 틀리면 **기동을 거부한다** — 조용히 무시돼 배포 후에야 로그인 실패로 알게 되는 상황을 막기 위함이다.
- 같은 이메일이 이미 있으면 비밀번호를 덮어쓰지 않는다. 재기동해도 안전하다.
- 계정을 만든 뒤에는 네 환경변수를 **지우고 다시 배포한다.**

마이그레이션 SQL로 넣지 않은 이유는 비밀번호 해시다 — SQL에 적으면 그 값이 저장소에 남고 모든 배포 환경이 같은 비밀번호를 쓰게 된다.

백엔드가 읽는 환경변수 전체 목록은 `backend/.env.example`에 있다. Spring Boot는 프론트(Next.js)와 달리 `.env`를 자동으로 읽지 않으므로, 그 파일은 목록이고 실제 주입은 배포 플랫폼의 환경변수 설정이나 셸 `export`로 한다.

### 로깅·헬스 체크

요청마다 `traceId`가 발급돼 그 요청에서 나온 모든 로그 줄에 붙는다(14번 §9.5). 앞단이 `X-Request-Id`를 주면 그 값을 이어 쓰고, 응답에도 같은 헤더로 돌려준다.

```
2026-09-03T20:31:02.914+09:00  INFO [a3f01c7d] ... : GET /api/products -> 200 (18ms)
```

**요청 본문·쿼리스트링·헤더는 로그에 남기지 않는다.** 12번 §5 P4가 `password`·`accessToken`·`Set-Cookie` 마스킹을 요구하는데, 애초에 기록하지 않으면 마스킹을 빠뜨릴 자리도 없다. 같은 이유로 SQL 파라미터가 새지 않도록 `org.hibernate.SQL` 레벨을 `INFO`로 고정해 뒀다.

헬스 체크는 인증 없이 열려 있고, 이 세 경로는 추적 로그를 남기지 않는다(로드밸런서가 초 단위로 찌른다).

| 경로 | 용도 |
|---|---|
| `/actuator/health` | 전체 상태 |
| `/actuator/health/liveness` | 프로세스가 살아 있는가 (재시작 판단) |
| `/actuator/health/readiness` | 트래픽을 받을 준비가 됐는가 (DB 접속 포함) |

상세 항목(`show-details`)은 노출하지 않는다 — DB 접속 정보가 익명에게 보이면 안 된다. 나머지 actuator 엔드포인트는 인증이 필요하다.

### 프론트엔드

```bash
cd frontend
cp .env.example .env.local    # NEXT_PUBLIC_API_BASE_URL — 없으면 모든 화면의 조회가 실패한다
npm install
npm run dev                   # http://localhost:3000
```

백엔드가 `http://localhost:8080`에 떠 있어야 한다(CORS는 `http://localhost:3000`만 허용한다).
